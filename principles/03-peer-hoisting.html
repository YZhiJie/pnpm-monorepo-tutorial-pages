P3 · peer 解析与 hoisting 内核 ​

前置：读完成 05 依赖共享与 Hoisting 控制　|　配套练习：E3 幻影依赖检测

「为什么我的 node_modules 里有个 node_modules？」「为什么同一个 react 装了两份？」——这两个高频疑问的答案，都在这一章。

你将学到 ​

  • hoisting（提升）到底把包提到了哪一层，谁看得到
  • hoist-pattern 与 public-hoist-pattern 的真实分工
  • peer 依赖的解析时机、冲突后果与多实例的成因
  • shamefully-hoist 为什么被称为「羞耻」开关

一、两种提升，两个目的地 ​

pnpm 的「提升」不是一种行为，而是两种，各自有独立的目的地：

开关目的地谁能看到本仓库取值
hoist + hoist-patternnode_modules/.pnpm/node_modules（隐藏的提升目录）所有 .pnpm 条目（内部可见）hoist=true，pattern 默认 ['*']
public-hoist-pattern项目根 node_modules/根目录下的任何代码与工具['*types*', '*eslint*']
bash
# 隐藏提升目录：本机实测约 420 个条目
ls node_modules/.pnpm/node_modules | wc -l

# 项目根：只有「公开提升」的包 + 根 package.json 显式声明的依赖
ls node_modules
# @babel  @changesets  @eslint  @iconify  @shikijs  @tutorial  @types
# @typescript-eslint  eslint  micromark-util-types  mime-types
# pkg-types  prettier  typescript  undici-types  vitepress

看懂上面这个列表，你就懂了 public-hoist-pattern[]=*types* 的威力：@types/*、@iconify/types、@shikijs/types、pkg-types、mime-types……只要名字里带 types，都会被提到项目根。本仓库正是靠它让 @types/node 这类类型包对所有包可见。

💡 为什么需要「隐藏提升目录」？ 因为历史上不少工具（构建脚本、CLI）会向上逐级查找 node_modules。把依赖提升到 .pnpm/node_modules，既能让这些工具找到东西，又不会把它们暴露给业务代码——兼顾兼容性与隔离性。

二、这些提升是谁决定的？看 .modules.yaml ​

pnpm install 会生成一份 node_modules/.modules.yaml，它是当前安装状态的真相：

yaml
# node_modules/.modules.yaml（节选）
hoistPattern:
  - "*"
publicHoistPattern:
  - "*types*"
  - "*eslint*"
hoistedDependencies:
  react-dom@18.3.1(react@18.3.1):
    react: private
    scheduler: private
    loose-envify: private

注意两点：

  1. hoistedDependencies 的 key 用了括号写法 react-dom@18.3.1(react@18.3.1)——与 P2 lockfile 的 snapshots key 完全同构；
  2. 值里的 private 表示「仅提升到隐藏目录，不公开」。想确认某个包到底被提到哪，直接读这个文件最快。
bash
# 排障用：查看当前安装的全部提升决策
cat node_modules/.modules.yaml

三、peer 依赖：解析时机与冲突后果 ​

peerDependencies 表达的是「我要求宿主环境提供某个包」，典型代表就是 React 组件库：

jsonc
// packages/ui/package.json
{
  "peerDependencies": {
    "react": ">=18.0.0",
    "react-dom": ">=18.0.0",
  },
}

它与 dependencies 的关键区别在于解析时机：

类型由谁提供实例冲突时
dependencies自己安装一份，独享不同版本即各装各的，互不干扰
peerDependencies宿主（消费者）提供宿主提供多套，则消费方也要多份实例

本仓库的两个开关（.npmrc 显式设置）：

配置取值含义
auto-install-peerstrue缺少 peer 时 pnpm 自动补装，减少警告
strict-peer-dependenciestruepeer 版本不满足时直接报错（默认是仅警告）

⚠️ 本仓库开启了 strict-peer-dependencies=true，所以 peer 不匹配会让安装失败而不是悄悄放过。这对库作者是好事（逼你写对范围），对使用老旧库的项目则可能很痛——出问题时先看这个开关。

冲突如何导致「同一份包装两遍」 ​

回忆 P1 的目录命名：

text
node_modules/.pnpm/react-dom@18.3.1_react@18.3.1/node_modules/react-dom
                            └── peer 上下文后缀
  • 若项目里只有 react 18 → 只会出现 react-dom@18.3.1_react@18.3.1 一个条目；
  • 若某依赖要求 react 17、另一个要求 react 18 → 出现 _react@17.x 与 _react@18.x 两个条目，各自链接到不同的 react 实例。

这就是「同一个包有两份」的机制来源：不是 pnpm 重复安装，而是不同的 peer 上下文必须隔离，否则会导致 A 用上 B 要求的 React 版本，进而引发 hooks 报错等诡异问题。

💡 所以当你看到 .pnpm 里出现两个 react，先别急着清理——先问「谁在要求另一个版本」。用 pnpm why react 就能顺藤摸瓜。

四、shamefully-hoist：为什么「羞耻」 ​

bash
# 等价于把一切都公开提升到根 node_modules
pnpm install --shamefully-hoist

它等价于 public-hoist-pattern=*，把所有包都摊平到项目根——行为退化成 npm 的扁平结构。后果：

  • ✅ 一些依赖「越级 require」的老库能跑了；
  • ❌ 幻影依赖全部复活，你会重新获得「代码引用了没声明的包也能跑」的虚假安全感；
  • ❌ 版本冲突无处隔离，node_modules 体积与不确定性同时上升。

因此它只应用于「迁移遗留项目、且短期内无法修依赖」的场景。本仓库在 .npmrc 里注释掉了这一项，保持 false。

五、排查工具箱 ​

bash
pnpm why react                      # 谁依赖了 react，为什么是这个版本
pnpm why -r clsx                    # 递归查看跨 workspace 的依赖来源
cat node_modules/.modules.yaml      # 当前提升决策
ls node_modules/.pnpm | grep react  # 看 peer 上下文是否造成了多实例
pnpm install --resolution-only      # 只重算依赖解析，不落盘安装

检查清单 ​

  • [ ] 能区分「隐藏提升」与「公开提升」的目的地与可见范围
  • [ ] 知道用 .modules.yaml 而不是猜来确认提升结果
  • [ ] 能解释 .pnpm 里出现两份同版本包的原因
  • [ ] 明白 shamefully-hoist 会用什么代价换来兼容性
