P5 · Changesets 版本计算 ​

前置：读完成 08 版本发布与 Changesets　|　配套练习：E5 Changesets 版本 bump

changeset version 一执行，一堆包的版本号就变了，CHANGELOG.md 也自动写好了。这一章拆开这个「黑盒」：版本号是怎么从几个 md 文件里算出来的。

你将学到 ​

  • changeset 文件的格式与语义
  • major / minor / patch 的 bump 规则与「多 changeset 合并」
  • changeset version 到底做了哪几件事
  • 依赖范围为什么会被自动改写
  • fixed 与 linked 两种版本联动策略的差异

一、changeset 文件长什么样 ​

开发者每完成一个改动，就跑一次 pnpm changeset，生成一个 md 文件（文件名随机，如 .changeset/tame-pandas-jump.md）：

md
---
"@tutorial/ui": minor
"@tutorial/utils": patch
---

新增 Card 组件的 loading 态，并修复 utils 的日期格式化边界问题。
  • frontmatter 里是包名 → bump 类型的映射；
  • 正文是给人看的变更说明，最终会进入 CHANGELOG.md；
  • 一个 changeset 可以同时影响多个包，这是 Monorepo 的关键便利：一次原子改动、一次版本决策。

二、bump 规则与合并 ​

单包的版本计算遵守语义化版本：

bump版本变化语义
patch1.2.3 → 1.2.4向后兼容的修复
minor1.2.3 → 1.3.0向后兼容的新功能
major1.2.3 → 2.0.0破坏性变更

多 changeset 合并时取「最高档」：

text
同一包被 patch + minor 命中 → 结果按 minor
同一包被 minor + major 命中 → 结果按 major

这正是「一个人的 patch 不会被另一个人的 major 覆盖掉」的保障。

💡 0.x 包的特殊性：0.x 阶段不存在稳定语义，社区通常把破坏性变更记在 minor 上。Changesets 会严格按你写的 bump 类型执行，具体对 0.x 的映射规则请以其官方文档为准——不要凭直觉假设。

三、changeset version 做了哪几件事 ​

bash
pnpm changeset          # 交互式生成 changeset（本地开发时用）
pnpm version            # 即 changeset version：应用所有 changeset

changeset version 会一次性完成：

  1. 读取 .changeset/ 下所有 changeset，按上面的规则合并出每个包的目标版本；
  2. 改写相关 package.json 的 version 字段；
  3. 依据正文生成/追加各包 CHANGELOG.md；
  4. 删除已消费的 changeset 文件（因此这些文件应提交进 git，而不是 gitignore）；
  5. 视配置联动改写包之间的依赖范围（见下一节）。

⚠️ 第 4 点意味着：changeset 文件本身是要提交的。若把它们加进 .gitignore，版本信息就永久丢失了。

四、依赖范围为什么会被自动改写 ​

当 @tutorial/utils 从 1.0.0 升到 1.1.0，而 @tutorial/ui 声明的是 "@tutorial/utils": "workspace:^"，会发生什么？

  • 仓库内：workspace:^ 指向本地包，代码上无需任何修改；
  • 发布时：按 第 06 章 的规则改写为 ^1.1.0。

这一切由 .changeset/config.json 的 updateInternalDependencies 控制：

jsonc
// 本仓库 .changeset/config.json
{
  "updateInternalDependencies": "patch", // 依赖版本超出范围时，自动给依赖者打 patch
  "baseBranch": "main",
  "linked": [["@tutorial/types", "@tutorial/utils", "@tutorial/ui"]],
  "fixed": [],
  "access": "restricted",
  "commit": false,
}

updateInternalDependencies: "patch" 的语义：某个包的依赖被升级、且新版本超出了依赖者声明的范围时，依赖者会自动获得一次 patch bump，并更新其依赖范围。

  • 设为 patch（默认）：范围失效才联动改动；
  • 设为 minor：联动改动时用更保守的档位。

五、fixed 与 linked：两种版本联动 ​

策略规则典型场景
fixed组内所有包版本号永远一致，任一包 bump → 全组一起升到同一版本强耦合的套件（如「全家桶」）
linked组内共享版本水位，各自可以是不同版本同一技术栈的多包，希望「要么都升、要么都不升」

本仓库把三个内部包配成了 linked：

jsonc
"linked": [["@tutorial/types", "@tutorial/utils", "@tutorial/ui"]]

含义是：这三者共享水位——其中任意一个 bump 时，其余包会一起被抬到「组内最高版本」，但各自保留自己的版本号。好处是避免出现「ui 是 1.3.0、utils 还停在 1.0.0」这种内部版本错位。

⚠️ 注意 access: "restricted"：本仓库所有包都是 "private": true，配置为受限发布，不会被推到公共 npm。要公开发布需改为 "public"（scoped 包还需付费组织账号）。

六、预发布模式 ​

bash
pnpm changeset pre enter beta    # 进入预发布：版本形如 1.1.0-beta.0
pnpm changeset version           # 递增预发布号：1.1.0-beta.1
pnpm changeset pre exit          # 退出，回到正式版本线

预发布期间每次发版只是递增后缀号，不会污染正式版本号——适合「内部灰度 → 正式发布」的节奏。

常见坑 ​

  • 忘记跑 pnpm changeset 就直接 changeset version → 没有 changeset，版本不会变（命令会提示）。
  • changeset 被 gitignore → 版本决策丢失，见上文第 4 点。
  • 在错误的分支上 version → baseBranch: main 用于判断「相对哪个分支计算」，分支策略乱了会出错。
  • 以为 workspace:* 会保留 * 到发布 → 不会，见 第 06 章。

检查清单 ​

  • [ ] 能写出一个合法的 changeset 文件（含 frontmatter 与正文）
  • [ ] 能说出多个 changeset 命中同一包时的合并规则
  • [ ] 知道 changeset version 会删除 changeset 文件
  • [ ] 能区分 fixed 与 linked 的联动方式
  • [ ] 亲手实现版本 bump 计算：练习 E5
