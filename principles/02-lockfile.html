P2 · lockfile 语义 ​

前置：读完成进阶篇　|　相关：原理篇 P1

pnpm-lock.yaml 常年被当成「别乱动的机器生成物」。但它其实是 Monorepo 一致性的唯一真相来源——看懂它，你就能解释 CI 为什么报 frozen-lockfile、为什么两台机器装出的依赖树不一样。

你将学到 ​

  • lockfile 四个顶层段落各自负责什么
  • importers 如何表达「每个 workspace 包各自声明了什么」
  • 为什么 v9 要把依赖分成 packages 与 snapshots 两段
  • --frozen-lockfile 与 prefer-frozen-lockfile 的判定差异

一、四个顶层段落 ​

本仓库为 lockfileVersion 9.0（对应 pnpm 9.x）：

yaml
lockfileVersion: "9.0"

settings: # 影响本次解析的开关（如 autoInstallPeers）
  autoInstallPeers: true
  excludeLinksFromLockfile: false

importers: # 每个 workspace 包「声明了什么」
  ...

packages: # 「要下载哪些东西」——按内容寻址建档
  ...

snapshots: # 「这些包之间怎么连线」——含 peer 上下文的解析结果
  ...

💡 一句话记忆：importers = 你的 package.json 汇总，packages = 下载清单，snapshots = 接线图。

二、importers：每个包的声明 ​

yaml
importers:
  .: # 仓库根（根 package.json）
    devDependencies:
      typescript:
        specifier: ^5.3.3
        version: 5.9.3

  packages/types: # 每个 workspace 包都是一个 importer
    dependencies: {}

  packages/ui:
    dependencies:
      "@tutorial/types":
        specifier: workspace:*
        version: link:../types # ← workspace 依赖在此显形
      clsx:
        specifier: ^2.1.0
        version: 2.1.1

两个关键点：

  1. 每个 workspace 包是一条独立的 importer，用相对根目录的路径作 key —— 这就是「每个包可以声明不同依赖」在锁文件里的表达。
  2. workspace 依赖记录为 link: 协议（version: link:../types）。它不指向 registry 上的任何版本，而是「软链接到本地目录」——正好对应 P1 里那条指向源码目录的软链接。

specifier 是你写在 package.json 里的原始声明，version 是解析后锁定的真实版本。二者分离的好处：解析结果被锁定，人可读的声明不受污染。

三、packages 与 snapshots：为什么要拆两段 ​

yaml
packages:
  clsx@2.1.1:
    resolution: { integrity: sha512-... } # 内容校验和

snapshots:
  clsx@2.1.1: {} # 无依赖时为空

  react-dom@18.3.1(react@18.3.1): # ← 带 peer 上下文的 key
    dependencies:
      loose-envify: 1.4.0
      react: 18.3.1
      scheduler: 0.23.2

拆段的意义在于把「内容」与「接线」解耦：

段落回答复用性
packages这个包是什么（版本、完整性校验和）同一份内容只记一次，与谁用它无关
snapshots它在某套 peer 组合下连了哪些依赖同版本包、不同 peer 组合 → 多条 snapshot

注意 react-dom@18.3.1(react@18.3.1) 的 括号写法：它正是 P1 里 .pnpm 目录名 react-dom@18.3.1_react@18.3.1 的「规范化写法」——同一个 peer 上下文，在锁文件用括号、在目录名用下划线。

resolution.integrity（sha512-...）就是 store 的内容指纹：pnpm 用它校验从 registry 下到的 tarball，也用它决定 store 里是否已有这份内容（内容寻址的直接体现）。

四、settings 与「一致性」 ​

yaml
settings:
  autoInstallPeers: true
  excludeLinksFromLockfile: false

settings 记录了解析时的关键开关。它存在的原因：同样的 package.json，在 autoInstallPeers 开/关下会解析出不同的树。把它写进锁文件，才能保证「换台机器、换个 CI，结果一致」。

这也是 Monorepo 的 shared-workspace-lockfile=true（本仓库 .npmrc 已显式开启）的价值所在：所有包共用一份锁文件，某个包升级依赖时，全局解析一起完成，不会出现「A 包锁 react 18、B 包锁 react 17 却互不知情」。

五、--frozen-lockfile 与 prefer-frozen-lockfile ​

选项行为
--frozen-lockfile要求锁文件与 package.json 完全一致；不一致 直接报错退出，不修改锁文件
prefer-frozen-lockfile（默认 true）pnpm install 时若锁文件已满足 package.json，跳过解析阶段直接按锁文件安装（headless，更快）；不满足才重新解析
—（CI 环境）pnpm 检测到 CI 环境时默认即 frozen，因此本地忘提交锁文件 → CI 立刻失败
bash
# 本地：想知道 CI 会不会过，先跑一遍 frozen 校验
pnpm install --frozen-lockfile

# 只想更新锁文件、不装包（例如只改了 package.json 想同步锁文件）
pnpm install --lockfile-only

⚠️ 最常见的 CI 事故：本地 pnpm add / pnpm remove 改了 package.json，却忘记提交 pnpm-lock.yaml，CI 用 --frozen-lockfile 直接 KO。本仓库的 ci.yml 全部 job 都使用 --frozen-lockfile。

检查清单 ​

  • [ ] 能说出 importers / packages / snapshots 各自负责什么
  • [ ] 能在锁文件里找到 workspace 依赖的 link: 记录
  • [ ] 能解释 react-dom@18.3.1(react@18.3.1) 括号的含义
  • [ ] 知道 CI 失败时先怀疑「锁文件没提交」
