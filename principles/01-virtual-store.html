P1 · Store 与符号链接算法 ​

前置：读完成入门篇 + 04 依赖共享　|　配套练习：E3 幻影依赖检测

「pnpm 省磁盘」这句话人人会说，但省在哪一层、硬链接挂在哪、软链接指向谁，多数人答不上来。这一章用你本机真实目录把这套「双层注入」算法拆开。

你将学到 ​

  • 全局 Store 的内容寻址（CAS）结构与硬链接导入方式
  • node_modules/.pnpm 虚拟存储的目录命名规则与内部结构
  • 项目 node_modules 里的软链接究竟指向哪里
  • 为什么这套结构能「从物理上」杜绝幻影依赖

一、三层结构总览 ​

text
① 全局 Store（跨项目共享，真正存文件的地方）
   ~/Library/pnpm/store/v11/files/<2位分片>/<128位十六进制>

② 虚拟存储（每个项目一份「包实例目录」的登记表）
   项目/node_modules/.pnpm/<name>@<version>_<peer后缀>/node_modules/<name>
        └─ 其中文件是 ① 的【硬链接】
        └─ 其依赖是同级 .pnpm 条目的【软链接】

③ 项目 / 各子包的 node_modules（你 require 时真正看的层）
   node_modules/<name>            → 软链接到 ②
   packages/ui/node_modules/react → 软链接到 ②
   packages/ui/node_modules/@tutorial/types → 软链接到源码目录（workspace 包）

一句话概括：文件只存 ①，② 负责「哪些包、哪些版本、配哪套 peer」，③ 只放软链接做「谁能看见谁」的访问控制。

二、全局 Store：内容寻址（CAS） ​

先看看你机器上的真实 store：

bash
pnpm store path
# /Users/<you>/Library/pnpm/store/v11      ← macOS 实际路径（注意不是 .npmrc 里写的路径）
bash
ls "$(pnpm store path)"
# .pnpm-needs-build-marker  .tmp  files  index.db  links  projects

关键在于 files/：按内容哈希存放，而不是按包名。

bash
ls "$(pnpm store path)/files" | head -5
# 00  01  02  03  04 ...                    ← 前两位十六进制做分片，防止单目录文件过多

ls "$(pnpm store path)/files/00" | head -3
# 00a250f585bdd6f18c19a983c0afd8ceddced0f7c86b36ca0d8306209557db65fc1ac7e3d9d0b921c4ec1c1690e37a66c3ba728593920c7eb78c6e8260db03
# ...

文件名是 SHA-512 的十六进制（128 个字符）——这就是「内容寻址」：内容相同的文件在 store 里只存在一份，无论被多少项目、多少个包引用。这是「省磁盘」的第一半。

  • files/：CAS 文件本体；
  • index.db：store 的索引（记录文件被哪些包引用、校验和等）；
  • links/、projects/：按项目记录链接关系，pnpm store prune 据此判断「哪些文件已无人引用」从而安全删除。

第二半省磁盘来自导入方式：从 store 到虚拟存储默认用硬链接（同一份文件、多个路径，不复制数据）。若文件系统不支持硬链接，pnpm 会退化为复制，可用配置干预：

bash
pnpm config get package-import-method   # auto | hardlink | copy | clone

💡 硬链接的本质：两个路径指向同一个 inode。删掉其中一个路径，数据仍在（只要还有另一个链接）。这就是为什么 node_modules 删了不心疼——数据在 store 里。

三、虚拟存储：node_modules/.pnpm ​

bash
ls node_modules/.pnpm | head -6
# @algolia+abtesting@1.26.0
# @algolia+autocomplete-core@1.17.7_@algolia+client-search@5.60.0_algoliasearch@5.60.0_search-insights@2.17.3
# ...

命名规则：

text
<scope/name 中的 / 换成 +>@<version>_<peerA>@<ver>_<peerB>@<ver>...
  • 无 peer 依赖时：clsx@2.1.1；
  • 有 peer 依赖时：把 peer 名与版本拼在后缀里，同版本包的不同 peer 组合 = 不同目录，从而各自拥有一份独立的依赖连线而不互相污染；
  • peer 后缀过长时，pnpm 会截断并追加一段哈希（上面第二条的 ..._search-insights@2.17.3、以及更长的 ..._rw7bhhuygnl3qme6yt7cuf2hnq 形式），避免文件名超出文件系统上限。

再看一个条目内部：

bash
ls node_modules/.pnpm/clsx@2.1.1/node_modules/
# clsx                          ← 包本体（文件为 store 的硬链接）

ls node_modules/.pnpm/react-dom@18.3.1_react@18.3.1/node_modules/
# loose-envify  react  react-dom  scheduler
# └─ 包本体 + 它的全部直接依赖（皆为指向各自 .pnpm 条目的软链接）

规律：.pnpm/<pkg>/node_modules/ 里放着「该包本体 + 它声明过的直接依赖」。因此 一个包运行时能 require 到什么，完全由它自己声明了什么决定——这就是幻影依赖被物理杜绝的原因。

四、项目 node_modules：软链接 ​

bash
ls -la packages/ui/node_modules/
# clsx        -> ../../../node_modules/.pnpm/clsx@2.1.1/node_modules/clsx
# react       -> ../../../node_modules/.pnpm/react@18.3.1/node_modules/react
# react-dom   -> ../../../node_modules/.pnpm/react-dom@18.3.1_react@18.3.1/node_modules/react-dom
# @tutorial/types -> ../../../types
# @tutorial/utils -> ../../../utils

两类链接值得区分：

类型指向说明
第三方包node_modules/.pnpm/<pkg>@<ver>/node_modules/<pkg>软链接，最终数据来自 store 硬链接
workspace 包源码目录（如 packages/types）软链接直指源码，改动即生效，这也是「本地开发零成本」的实现基础

⚠️ 注意：workspace 包不经过 store。所以你在 packages/ui 里改一行代码，apps/web 立刻看到——因为它链接的就是源码目录本身，并非某个已构建产物。（这也解释了为什么包需要自己 build 才能产出 dist。）

.bin/ 目录里则是 CLI 可执行文件的 shim，同样通过软链接/垫片脚本指向 .pnpm 中对应包的 bin。

五、可调项与排障 ​

配置作用风险
store-dir全局 store 位置放在慢盘上会拖慢所有项目
virtual-store-dirnode_modules/.pnpm 的位置（默认即 node_modules/.pnpm）一般不要改
package-import-method硬链接 / 复制 / clonecopy 会失去省磁盘特性，但可跨文件系统使用

实测踩坑（本仓库真实存在）：.npmrc 里写了 store-dir=~/.pnpm-store，但 pnpm store path 返回的是 ~/Library/pnpm/store/v11——~ 并未按预期展开，配置实际未生效。

✅ 原则：永远用 pnpm store path 确认实际路径，不要假设配置文件里的路径一定生效。

常用排障命令：

bash
pnpm store path          # 实际 store 位置
pnpm store status        # 校验 store 完整性
pnpm store prune         # 清理无引用的文件（释放空间）
du -sh "$(pnpm store path)"      # store 占用
du -sh node_modules              # 项目占用（对比可见省了多少）

检查清单 ​

  • [ ] 能画出 store → .pnpm → node_modules 三层流向
  • [ ] 能解释 .pnpm 目录名里的 _peer@version 后缀为何存在
  • [ ] 能用 ls -la 分辨「第三方包软链接」与「workspace 源码软链接」
  • [ ] 知道用 pnpm store path 而非 .npmrc 来确认真实 store 位置
