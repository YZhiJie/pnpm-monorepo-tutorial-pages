P4 · 拓扑排序与并行构建 ​

前置：读完成 07 构建流程与缓存优化　|　配套练习：E4 拓扑排序与并行调度

「为什么我在 packages/ui 改了代码，apps/web 构建时用的还是旧的？」——这类问题的答案往往不在构建工具，而在 Monorepo 的调度顺序。

你将学到 ​

  • 依赖图如何决定「谁先构建」
  • -r 默认的拓扑序、--parallel 的区别、并发度怎么控
  • 缓存命中的判定本质（输入指纹）
  • 三层缓存：TS 增量、Vite 预构建、任务级缓存

一、依赖图与拓扑序 ​

把 workspace 的每个包看作节点，把 package.json 里的 workspace 依赖看作边：

text
          ┌──────────────┐
          │ packages/types│  ← 无依赖，图的「源点」
          └───────┬──────┘
        ┌─────────┴──────────┐
        ▼                    ▼
┌───────────────┐    ┌───────────────┐
│ packages/utils│    │   apps/api    │
└───────┬───────┘    └───────────────┘
        ▼
┌───────────────┐
│  packages/ui  │
└───────┬───────┘
        ▼
┌───────────────┐
│   apps/web    │  ← 消费最多的「汇点」
└───────────────┘

拓扑序（topological order） 指：任一节点出现前，它依赖的所有节点都已出现。对本仓库就是 types → utils → ui → web。

违背拓扑序的后果很具体：apps/web 构建时需要 @tutorial/ui 的产物，而 ui 又需要 utils 的类型定义——顺序错了，要么报错，要么悄悄用了上一次的旧产物。

二、pnpm 的调度行为 ​

命令顺序适用场景
pnpm -r run build拓扑序（被依赖者先）有产物依赖时（默认行为，最省心）
pnpm -r --parallel run dev忽略顺序，全部同时启动长驻进程（dev server）
pnpm -r run typecheck拓扑序类型检查（跳不过依赖）
pnpm --filter ...@tutorial/types run build只跑「依赖了 types」的包（含传递依赖者）精准重建

本仓库根 package.json 就是两种策略的对照：

jsonc
{
  "scripts": {
    // 显式拓扑：先 packages 层，再 apps 层
    "build": "pnpm -r --filter=./packages/* run build && pnpm -r --filter=./apps/* run build",
    // 无关顺序，全部并行
    "dev": "pnpm -r --parallel run dev",
    // 借助 pnpm 默认的拓扑序
    "test": "pnpm -r run test",
    "typecheck": "pnpm -r run typecheck",
  },
}

💡 build 采用「两段 filter」而非单条 -r run build，是一种显式拓扑写法：不依赖 pnpm 的排序推断，层级关系一眼可读。当层数变多（如 tools/、examples/）时，这种写法反而更难维护——那时更适合交给 pnpm 的默认拓扑序或任务编排工具。

并发度控制：

bash
pnpm -r --workspace-concurrency 4 run build   # 限制同时跑 4 个包
pnpm -r --workspace-concurrency 1 run build   # 串行（等价于严格拓扑，便于排查顺序问题）

三、缓存的本质：输入指纹 ​

所有「增量构建 / 缓存命中」的机制，本质都是同一件事：

text
输入指纹 = hash(源文件内容 + 依赖包的产物 + 构建配置 + 环境变量)
命中条件 = 该指纹此前算过，且产物仍在

因此缓存失效的常见原因不是「工具坏了」，而是输入变了：改了一行源码、依赖包重新构建、tsconfig 动了一下、甚至注入了一个新的环境变量。

三层缓存，粒度从细到粗：

层次载体命中后节省
类型检查*.tsbuildinfo（TS incremental / composite）跳过未变文件的类型计算
依赖预构建node_modules/.vite/（Vite dep pre-bundling）跳过第三方依赖的打包
任务级.turbo/、.nx/ 等（如 Turborepo）整个包的构建任务直接跳过

⚠️ 本仓库现状：目前 packages/* 的 tsconfig.json 未开启增量，仓库内也不存在 *.tsbuildinfo 与 node_modules/.vite。也就是说，下面这些优化是你可以动手加上的，而不是已经生效的。

bash
find . -name '*.tsbuildinfo' -not -path './node_modules/*'   # 当前：无输出

四、落地到本仓库 ​

① 打开 TypeScript 增量（改 packages/*/tsconfig.json）：

jsonc
{
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": "dist/.tsbuildinfo",
  },
}

或使用 Project References（composite: true + 根 tsconfig 的 references），让 tsc -b 自动按依赖拓扑构建并复用增量信息。

② 只跑改动过的包（CI 提速最有效的一招）：

bash
pnpm -r --filter ...[origin/main] typecheck
pnpm -r --filter ...[origin/main] run build

...[<ref>] 会选出「自该 ref 以来发生变更的包 及其依赖者」——注意是依赖者（因为它们的产物也依赖被你改动的东西）。

③ 验证效果：

bash
time pnpm build        # 第一次
time pnpm build        # 第二次：若已开启增量，应明显更快

检查清单 ​

  • [ ] 能画出本仓库的依赖图并写出拓扑序
  • [ ] 能说清 -r（拓扑）与 --parallel（无序）的适用差异
  • [ ] 理解缓存判定 = 输入指纹，而非「工具的黑魔法」
  • [ ] 会用 --filter ...[origin/main] 只构建改动包
  • [ ] 亲手实现拓扑排序：练习 E4
