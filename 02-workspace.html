02 工作区配置与目录设计 ​

本章详解 pnpm-workspace.yaml 的每一项配置、模块化目录结构设计原则及非标准结构的适配方案。

配套漫画：

目录 ​

  • workspace 范围定义
  • 目录结构设计
  • pnpm-workspace.yaml 配置详解
  • 非标准结构适配
  • 跨包引用机制

workspace 范围定义 ​

核心文件：pnpm-workspace.yaml ​

yaml
# pnpm-workspace.yaml
packages:
  # apps/* 表示 apps 目录下的所有子目录（单层）
  - "apps/*"
  # packages/* 表示 packages 目录下的所有子目录（单层）
  - "packages/*"
  # 也可指定具体目录（非 glob 模式）
  - "legacy/libs/shared"

  # 排除规则：以 ! 开头表示排除
  # 排除 apps/mobile 目录（如项目已废弃）
  - "!apps/mobile"
  # 排除所有以 test- 开头的目录（测试脚手架）
  - "!apps/test-*"
  # 排除任何层级的 template 目录
  - "!**/template"

范围匹配规则 ​

模式含义示例
apps/*单层匹配apps/web 匹配，apps/web/src 不匹配
apps/**多层匹配apps/web/src 也匹配
packages/ui-*前缀匹配packages/ui-button、packages/ui-input
!apps/**排除apps/ 下所有目录被排除

优先级与冲突 ​

  • 后定义的排除规则会覆盖前面的包含规则
  • 列表顺序从上到下依次匹配，一旦匹配即停止

目录结构设计 ​

推荐目录结构 ​

project-root/
├── apps/                          # 可部署应用
│   ├── web/                       # Web 应用
│   ├── mobile/                    # 移动端应用
│   ├── admin/                     # 后台管理系统
│   └── api/                       # 后端服务
│
├── packages/                      # 共享库
│   ├── ui/                        # UI 组件库
│   ├── utils/                     # 工具函数库
│   ├── types/                     # TypeScript 类型定义
│   ├── config/                    # 共享配置（eslint、tsconfig）
│   └── hooks/                     # React Hooks 库
│
├── tools/                         # 构建工具与脚本
│   ├── scripts/                   # 自动化脚本
│   ├── ci/                        # CI/CD 相关脚本
│   └── generators/                # 代码生成器
│
├── docs/                          # 文档
├── .changeset/                    # 版本变更记录
├── .github/workflows/             # CI 配置
├── pnpm-workspace.yaml
├── package.json                   # 根 package.json（scripts + devDeps）
└── tsconfig.json                  # 根 TypeScript 配置

设计原则 ​

原则 1：应用与库分离（apps/packages） ​

yaml
# pnpm-workspace.yaml
packages:
  - "apps/*" # 应用：可独立部署的端侧产品
  - "packages/*" # 库：被复用的模块，不可独立部署

原则 2：按业务域分层 ​

yaml
packages:
  # 应用层
  - "apps/customer-portal"
  - "apps/admin-dashboard"

  # 共享层（核心工具）
  - "packages/core"
  - "packages/shared"

  # 功能层（按业务域划分）
  - "packages/auth"
  - "packages/payment"
  - "packages/analytics"

原则 3：扁平 vs 嵌套 ​

扁平结构（推荐大多数项目）：

packages/
  ├── ui/
  ├── utils/
  ├── types/
  └── hooks/

嵌套结构（大型项目，需二次分组）：

packages/
  ├── foundation/
  │   ├── types/
  │   ├── utils/
  │   └── config/
  ├── ui/
  │   ├── components/
  │   └── theme/
  └── business/
      ├── auth/
      └── payment/

目录命名规范 ​

命名方式示例适用场景
kebab-casemy-component、auth-service包名（npm 包名规范）
camelCasemyComponent不推荐目录名使用
PascalCaseMyComponent组件目录（可选）
lowercaseui、utils、api通用工具目录（推荐）

pnpm-workspace.yaml 配置详解 ​

完整配置示例 ​

yaml
# 包范围定义（必需）
packages:
  - "apps/*"
  - "packages/*"
  - "!**/test/**"

# 共享 lockfile（默认 true）
# true: 所有包共享根目录的 pnpm-lock.yaml
# false: 每个包独立管理 lockfile（不推荐，失去一致性）
shared-workspace-lockfile: true

# 优先使用 workspace 包（默认 true）
# true: 当 package.json 声明 workspace 包时，优先使用本地版本
# false: 即使本地有 workspace 包，也从 registry 下载
prefer-workspace-packages: true

# 自动链接 workspace 包（默认 true）
# true: 自动创建本地软链接
# false: 需显式使用 workspace:* 才会链接
link-workspace-packages: true

# save-workspace-protocol: 安装时自动添加 workspace: 前缀
# true: 总是添加 workspace:*
# false: 不添加（使用 registry 版本号）
# rolling: 安装时添加 workspace:*，发布时转换为 ^x.x.x
save-workspace-protocol: rolling

配置项关联关系图 ​

packages                 # 定义哪些目录属于 workspace
    │
    ├── shared-workspace-lockfile   # 是否统一 lockfile
    │       └── true（推荐）：pnpm-lock.yaml 在根目录
    │
    ├── prefer-workspace-packages   # 是否优先本地包
    │       └── true（推荐）：本地有则不用 registry
    │
    ├── link-workspace-packages     # 是否自动软链接
    │       └── true（推荐）：本地包自动链接
    │
    └── save-workspace-protocol     # 安装时是否加前缀
            └── rolling（推荐）：开发用 workspace:*，发布变版本号

非标准结构适配 ​

场景 1：遗留项目已有固定目录 ​

yaml
# 原项目结构：
# src/
#   modules/
#     module-a/
#     module-b/
#   services/
#     service-a/
#     service-b/

packages:
  - "src/modules/*"
  - "src/services/*"

场景 2：Monorepo 中混有单仓库（polyrepo）遗留代码 ​

yaml
packages:
  # 新 monorepo 结构
  - "apps/*"
  - "packages/*"
  # 遗留独立项目（仍使用独立 node_modules）
  - "legacy/project-a"
  - "legacy/project-b"

场景 3：包分散在多个子目录层级 ​

yaml
packages:
  # 单层匹配
  - "packages/*"
  # 多层匹配（如 packages/frontend/button、packages/backend/api）
  - "packages/**/*"
  # 排除 examples 和 docs
  - "!packages/**/examples"
  - "!packages/**/docs"

跨包引用机制 ​

workspace: 协议详解 ​

json
// package.json
{
  "dependencies": {
    // workspace:*   始终链接到本地最新版本（开发推荐）
    "@tutorial/ui": "workspace:*",

    // workspace:^   链接到本地版本，遵循 ^ 语义
    "@tutorial/utils": "workspace:^",

    // workspace:~   链接到本地版本，遵循 ~ 语义
    "@tutorial/types": "workspace:~",

    // 固定版本号：发布时不会被替换（不推荐 workspace 内使用）
    "lodash": "^4.17.21"
  }
}

协议行为对比 ​

协议开发期行为发布时行为适用场景
workspace:*软链接到本地转换为 ^x.x.x开发推荐，默认使用
workspace:^软链接到本地保持 ^x.x.x允许小版本兼容
workspace:~软链接到本地保持 ~x.x.x仅允许补丁版本兼容
workspace:x.x.x软链接到本地保持 x.x.x固定版本依赖

发布时的版本替换 ​

bash
# 开发时依赖声明
"@tutorial/ui": "workspace:*"

# 发布到 registry 前自动替换为
"@tutorial/ui": "^1.2.3"

# 替换规则由 .npmrc 中的 save-workspace-protocol 控制

最佳实践 ​

1. 根 package.json 的职责 ​

json
{
  "name": "monorepo-root",
  "private": true,
  "scripts": {
    "dev": "pnpm -r --parallel run dev",
    "build": "pnpm -r run build",
    "test": "pnpm -r run test",
    "lint": "pnpm -r run lint"
  },
  "devDependencies": {
    "@changesets/cli": "^2.27.1",
    "typescript": "^5.3.3"
  }
}

2. 跨包 tsconfig 继承 ​

json
// 根 tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true
  }
}

// apps/web/tsconfig.json
{
  "extends": "../../tsconfig.json",
  "compilerOptions": {
    "jsx": "react-jsx",
    "paths": {
      "@tutorial/*": ["packages/*/src"]
    }
  }
}
