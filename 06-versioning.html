语义化版本规范 ​

版本号格式：MAJOR.MINOR.PATCH ​

字段含义变更场景示例
MAJOR主版本不兼容的 API 变更1.0.0 → 2.0.0
MINOR次版本向下兼容的功能新增1.0.0 → 1.1.0
PATCH补丁向下兼容的问题修复1.0.0 → 1.0.1

预发布版本 ​

标识含义示例使用场景
alpha内部测试1.0.0-alpha.1功能开发中，不稳定
beta公开测试1.0.0-beta.2功能基本完成，待反馈
rc候选发布1.0.0-rc.1即将正式发布，仅修复 bug

版本范围符号 ​

符号含义示例等价范围
^兼容版本^1.2.3>=1.2.3 <2.0.0
~近似版本~1.2.3>=1.2.3 <1.3.0
>=最低版本>=1.2.3无上限
=精确版本=1.2.3仅 1.2.3
*任意版本*所有版本

Changesets 核心概念 ​

什么是 Changesets？ ​

Changesets 是一个用于管理 monorepo 版本与变更日志的工具，核心思想是：

  • 每个变更都显式声明：开发者创建 changeset 文件描述本次改动
  • 自动计算版本：根据 changeset 类型自动决定 bump 级别
  • 自动生成 CHANGELOG：汇总所有 changeset 生成发布日志

安装与初始化 ​

bash
# 安装
pnpm add -Dw @changesets/cli

# 初始化
pnpm changeset init

Changeset 文件结构 ​

markdown
// .changeset/wise-pandas-dance.md
---

'@tutorial/ui': minor
'@tutorial/utils': patch
---

feat: 新增 Button 组件 loading 状态
fix: 修复 utils 中 deepClone 循环引用问题

变更类型映射 ​

Changeset 类型版本 bump适用场景
majorMAJOR +1破坏性变更（breaking change）
minorMINOR +1新功能（feature）
patchPATCH +1修复（fix）、文档（docs）

本仓库的 types / utils / ui 起始版本均为 0.0.0，首个 minor changeset 会把它们带到 0.1.0，符合“尚未稳定”的教程叙事。apps/* 仍是 private: true，不参与发布。

版本发布流程 ​

完整流程 ​

bash
# 1. 创建 changeset（每次功能开发后）
pnpm changeset

# 交互式选择：
# - 哪些包受到影响？
# - 变更类型（major/minor/patch）？
# - 变更描述？

# 2. 版本计算（合并所有 changeset）
pnpm version:packages
# 等价于 changeset version；会更新版本号、生成 CHANGELOG、删除已消费的 changeset
# 注意：`pnpm version` 是 pnpm 内置命令，不会执行本仓库脚本，必须带 `:packages` 后缀

# 3. 发布前检查（构建、测试、changeset status、pack、publint）
pnpm release:check

# 4. 发布到 registry（build + changeset publish）
pnpm release

从 0.0.0 到首次发布（当前仓库状态） ​

为什么现在刻意停在未发布状态 ​

仓库目前有三个可发布包，版本都是 0.0.0，并保留了 5 个尚未消费的 changeset。本批只做发布叙事与校验，不执行 changeset version，原因是：

  • 一旦消费 changeset，三个包会变成 0.1.0，但 registry 上并不存在这个版本，仓库会进入“版本号已前进、发布事实没发生”的中间态；
  • changeset 文件被删除后，首次发布的变更叙事只能靠 CHANGELOG 回溯，评审时少了一份可直接对照的意图记录；
  • 本次既不 push、也不打 tag、也不发布，提前改版本会让后续 release PR 的 diff 混入无关改动；
  • 保持 0.0.0 时，pnpm version:check 可以明确校验“未发布状态 + 5 个 changeset + 首个发布目标 0.1.0”三者一致。

完整操作序列 ​

以下步骤只在真正决定发布时执行，日常开发不应提前跑第 2 步：

  1. 冻结变更范围：确认本批要发布的包与 changeset 都已合入，pnpm changeset status 的输出符合预期。
  2. 计算版本：在独立分支执行 pnpm version:packages。Changesets 会更新 package.json、生成包级 CHANGELOG.md，并删除已消费的 changeset。
  3. 检查版本 diff：三个库应为 0.1.0，apps/* 保持 1.0.0；确认没有意外的 major/minor 跳级。
  4. 同步文档版本：把 .github/RELEASE_NOTES_TEMPLATE.md 的版本计划表改为「当前版本 0.1.0 / 意图 无 / 首个发布版本 0.1.0」；根 CHANGELOG.md 仍标「未发布」。此时 pnpm version:check 应通过，并提示“版本已推进，待 registry 发布”。
  5. 同步 lockfile：执行 pnpm install --lockfile-only，预期无 diff；若有 diff，说明依赖声明或 catalog 被意外改写。
  6. 提交版本变更：建议使用 chore(release): version packages，把 package.json、包级 CHANGELOG、release notes 表与 changeset 删除放在同一个提交里，便于整批回滚。
  7. 跑发布门禁：pnpm release:check、pnpm docs:build、pnpm format:check。版本提交后没有 changeset，release:check 会跳过 changeset status，直接使用 package.json 版本。
  8. 创建 tag：按下面的命名建议创建仓库级 tag；changeset publish 还会为每个包自动创建 包名@版本号 tag。
  9. 发布：npm_config_registry=https://registry.npmjs.org pnpm release。仓库 .npmrc 默认指向 npmmirror，镜像源通常不允许发布，必须显式覆盖 registry。
  10. 填写 release notes 与复核：按 .github/RELEASE_NOTES_TEMPLATE.md 汇总版本、兼容矩阵、安装命令与已知风险；用 npm view @tutorial/utils versions、npm dist-tag ls @tutorial/utils 复核后，再把根 CHANGELOG.md 的状态改为“已发布”。

第 2 步与第 9 步之间不要间隔太久。长期停留在“已计算版本但未发布”会让文档、lockfile 与 registry 三方看起来都不一致。

tag 命名建议（当前不要创建） ​

方案示例优点代价
仓库级统一 tagv0.1.0与教程版本叙事、GitHub Release 一一对应独立版本后无法表达各包差异
Changesets 自动分包 tag@tutorial/types@0.1.0 等与 npm 发布事实严格对应三个 tag 较碎，Release 需要额外汇总
两者并存（推荐首次使用）v0.1.0 + @tutorial/*@0.1.0兼顾里程碑叙事与发布事实需明确以分包 tag 作为发布事实

首次发布时三个包都会到 0.1.0，因此 v0.1.0 不会产生歧义；后续若各包版本分化，应以分包 tag 为准，v* tag 只标记教程/样板的重要节点。

版本通道 ​

snapshot（临时验证版本） ​

bash
# 生成形如 0.0.0-canary-20261104145442 的版本，用于联调或临时验证
pnpm version:snapshot

# 用 canary dist-tag 发布（示例，实际发布还需要 registry 凭据）
pnpm release:tag canary

changeset version --snapshot <name> 的关键行为：

  • 版本号形如 <当前版本>-<name>-<时间戳>，不消耗正式的 minor/major 语义；
  • 会删除已消费的 changeset 文件，因此必须在临时分支或临时工作副本中执行；
  • 验证完成后用 git checkout -- . 恢复被改写的 package.json / CHANGELOG.md，避免把 snapshot 版本提交进主分支。

预发布（alpha / beta / rc） ​

bash
# 1. 进入预发布模式（会在 .changeset/pre.json 记录状态，必须提交）
pnpm pre:enter alpha

# 2. 计算预发布版本：0.0.0 + minor → 0.1.0-alpha.0
pnpm version:packages

# 3. 用对应 dist-tag 发布
pnpm release:tag alpha

# 4. 退出预发布模式，再执行一次正式版本计算
pnpm pre:exit
pnpm version:packages

实测输出（types / utils）：

阶段版本
初始0.0.0
pre enter alpha + version0.1.0-alpha.0
pre exit + version0.1.0
snapshot canary0.0.0-canary-<timestamp>

pre.json 会被写入 .changeset/，它记录了预发布 tag、初始版本和已消费的 changeset。忘记 pre:exit 时，后续 version 会继续产出 -alpha.N 版本。

dist-tag（发布渠道） ​

bash
# 指定发布渠道：latest / next / beta / canary
pnpm release:tag next

# 等价的手工操作
npm publish --tag next

dist-tag 只是 registry 上的“别名”，不改变版本号本身。用户可以显式安装非 latest 渠道：

bash
pnpm add @tutorial/utils@next
pnpm add @tutorial/utils@0.1.0-beta.1

发布前检查 ​

导出 changeset 状态 ​

bash
# 输出 JSON，便于 CI 或脚本消费
pnpm exec changeset status --output release-status.json

release-status.json 结构（节选）：

json
{
  "changesets": [{ "id": "publishable-libs", "summary": "..." }],
  "releases": [
    { "name": "@tutorial/types", "type": "minor", "newVersion": "0.1.0" }
  ]
}

一条命令跑完检查 ​

bash
pnpm release:check

scripts/release-check.mjs 依次执行：

  1. pnpm build：构建全部产物，确保 dist 是最新的；
  2. pnpm test：跑全量测试（根 test 脚本会先构建共享包）；
  3. 若仍有 changeset，执行 changeset status --output release-status.json 确认待发布版本；版本提交后 changeset 已被消费，则跳过该步，直接使用 package.json 版本；
  4. 对每个非 private 包执行 pnpm pack，检查 tarball 中只有 package.json、dist/ 与自动附带的 LICENSE，且不残留 workspace: 协议；
  5. pnpm dlx publint --strict：校验 exports / types / 模块格式是否自洽。

apps/* 是 private: true，会被明确跳过；这与 changeset publish 的发布行为一致。三个库包（types / utils / ui）都可发布。

手工检查清单 ​

bash
# 检查 workspace 依赖是否已替换（dry-run 不联网上传）
# 仓库 .npmrc 默认指向 npmmirror，这里显式覆盖到 npmjs，避免误判发布目标
pnpm publish --dry-run --no-git-checks --registry https://registry.npmjs.org

# 检查 tarball 内容（pnpm pack 会直接打印文件清单）
pnpm pack --pack-destination /tmp/pack

# 产物结构自检
pnpm dlx publint --strict .

发布包应满足：

  • 包内只包含 files 白名单声明的内容（通常是 dist），不含源码、测试与构建缓存；
  • exports 的 import / require 分别指向 dist/esm 与 dist/cjs，并在各自目录内用 package.json 标记模块格式；
  • workspace:* 会在 pnpm pack / publish 时改写为具体版本，tarball 中不应残留协议写法；
  • private: true 的包（如 apps/*）不会发布，但它的 changeset 仍会被记录。

产物消费的本地验收 ​

bash
# 1. 生成 tarball（版本号以当前 package.json 为准，当前为 0.0.0）
pnpm --dir packages/types pack --pack-destination /tmp/pack

# 2. 在临时目录安装并验证 CJS / ESM / 类型
mkdir -p /tmp/consumer && cd /tmp/consumer
npm init -y
npm install /tmp/pack/tutorial-types-0.0.0.tgz
node -e "require('@tutorial/types')"
node --input-type=module -e "import('@tutorial/types')"

这一步验证的是“发布后的包”，而不是 workspace 里的源码软链。只要 pnpm pack 的产物能独立安装并通过导入检查，发布链路才算闭环。

版本同步策略 ​

固定版本模式（Fixed） ​

所有包使用相同版本号，任何变更触发全量发布：

json
// .changeset/config.json
{
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "fixed": [["@tutorial/*"]],
  "linked": [],
  "access": "public",
  "baseBranch": "main"
}

独立版本模式（Independent） ​

每个包独立维护版本号：

json
{
  "fixed": [],
  "linked": []
}

本仓库采用独立版本模式：linked 为空，access 为 public。types / utils / ui 均可发布，apps/* 为 private 且 privatePackages.version 为 false；因此应用不会联动 bump，也不会生成包级 CHANGELOG，发布时同样会被跳过。

选择独立版本的原因：三个库的职责与发布节奏不同（ui 的样式契约、types 的类型定义、utils 的运行时函数），固定版本会让一次 ui 改动强制 bump 两个与本次无关的包，产生无意义的版本膨胀。

模式优点缺点适用场景
Fixed版本一致，易于理解无变更的包也被 bump强耦合包组
Linked部分同步配置复杂中等耦合包组
Independent灵活，按需发布版本碎片化松散耦合包组

配置语义 ​

updateInternalDependencies ​

控制“被依赖包升级后，内部依赖方是否/如何跟着升级”：

json
{
  "updateInternalDependencies": "patch"
}
  • 默认值 "patch"：当 types 升级导致 utils 声明的依赖范围需要改写时，utils 至少获得一次 patch bump；
  • 可设为 "minor"：依赖方至少获得 minor bump，适合“依赖升级也算功能变化”的项目；
  • 该选项只影响包间依赖范围维护，不会改变 changeset 里显式声明的 bump 级别。

本仓库保留 "patch"：utils 依赖 types，types 发版时 utils 的依赖范围需要同步，patch 已足够表达“兼容性维护”。

privatePackages ​

发布预演暴露了一个联动副作用：updateInternalDependencies: "patch" 会让依赖可发布包的私有应用也获得 patch bump。apps/* 不发布，这种版本变化没有意义，还会生成只有“Updated dependencies”的空 CHANGELOG。

json
{
  "privatePackages": {
    "version": false,
    "tag": false
  }
}
  • version: false：私有包不参与版本计算，apps/api、apps/web 保持 1.0.0；
  • tag: false：私有包不创建 tag；version 为 false 时该值必须为 false；
  • 预演复测：配置后两个应用版本不变，也不再生成 apps/*/CHANGELOG.md。

bumpVersionsWithWorkspaceProtocolOnly ​

json
{
  "bumpVersionsWithWorkspaceProtocolOnly": true
}
  • 默认 false：任何内部依赖方都会被检查并可能 bump；
  • 设为 true：只有用 workspace: 协议声明依赖的包才会被联动 bump；
  • 本仓库所有内部依赖都是 workspace:*，两种取值对现有包的结果一致，因此暂不显式开启；当未来出现直接写 ^0.1.0 的 registry 范围依赖时，再按需开启以避免误 bump。

fixed vs linked ​

配置版本关系发布行为典型场景
fixed组内所有包始终同版本任一包变更，组内所有包一起 bumpReact 生态同版本套件
linked组内包发布时联动，但允许版本不一致有变更的包发布时，组内版本向高版本对齐版本接近但可独立发版的包组
独立版本每个包完全独立只发布有 changeset 的包松散耦合的工具库

回滚与 tag ​

发布后的 git tag ​

changeset publish 会为每个发布成功的包创建 包名@版本号 形式的 tag，例如：

bash
git tag --list "@tutorial/*"
# @tutorial/types@0.1.0
# @tutorial/utils@0.1.0

tag 是发布事实的记录，不要为了“重发”而删除已有 tag。如果发布内容有问题，优先走下面的 dist-tag / deprecate 流程，再用新版本修复。

切换 dist-tag ​

bash
# 查看现有渠道
npm dist-tag ls @tutorial/utils

# 把 latest 指向一个已知稳定的旧版本
npm dist-tag add @tutorial/utils@0.1.0 latest

# 新增 next 渠道
npm dist-tag add @tutorial/utils@0.1.1 next

# 删除某个渠道
npm dist-tag rm @tutorial/utils next

适用场景：新版本刚发出但发现回归，先把 latest 回退到稳定版本，用户重新安装即可恢复；随后发布修复版本，再把 latest 指回新版本。

标记废弃版本 ​

bash
npm deprecate @tutorial/utils@0.1.1 "存在回归问题，请升级到 0.1.2"

deprecate 不会删除包，只是让安装时出现警告，是比 unpublish 更安全的止损手段。

回滚 runbook ​

  1. 确认影响范围：npm view @tutorial/utils versions、npm dist-tag ls、对比 CHANGELOG。
  2. 切走 latest：npm dist-tag add @tutorial/utils@<上一个稳定版本> latest。
  3. 标记问题版本：npm deprecate @tutorial/utils@<问题版本> "<原因>"。
  4. 修复并发布新 patch：提交 fix → pnpm changeset（patch）→ pnpm version:packages → pnpm release:check → pnpm release。
  5. 必要时回滚代码：git revert <发布提交>，但不要复用已发布的版本号。
  6. 最后再考虑 unpublish：npm 仅允许在发布后 72 小时内取消发布，且会受下游已安装/已缓存影响；多数情况下应使用 deprecate + 新版本。

发布是不可逆操作：同一个版本号不能二次发布。任何“重发”都必须通过提升版本号完成。

最佳实践 ​

1. 提交规范与 Changeset 关联 ​

bash
# Conventional Commits 与 changeset 类型映射
feat: xxx          → minor
fix: xxx           → patch
BREAKING CHANGE:   → major

commitlint.config.js 负责校验提交信息格式，Changesets 负责声明版本影响，两者职责分开：commit 描述“改了什么”，changeset 描述“对版本意味着什么”。

2. 版本 PR 与发布分离 ​

推荐流程：

  1. 功能 PR 里同时提交 changeset；
  2. 合并到 main 后，由维护者执行 pnpm version:packages，提交 chore(release): version packages；
  3. 版本提交合并后，.github/workflows/release.yml 负责构建、校验与发布。

这样做的好处是版本变更可 review、可回滚，避免 CI 在每次 push 时自动改版本。

3. 发布前永远先跑 release:check ​

bash
pnpm release:check && pnpm release

release:check 覆盖版本一致性、构建、测试、changeset 状态、tarball 内容与 publint；任何一步失败都不应继续发布。

4. 本地不要开启 provenance ​

provenance 依赖 GitHub Actions 的 OIDC 身份，只在 CI 中通过 NPM_CONFIG_PROVENANCE=true 开启。本地 pnpm release 保持关闭，否则会因缺少 OIDC 环境而直接失败。
