Turborepo 任务缓存（本仓库实际方案） ​

根 package.json 的 build / test / lint 已切到 Turbo 2.x，同时保留 build:pnpm 作为纯 pnpm 拓扑构建的对照路径。

json
// turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    },
    "test:unit": {
      "outputs": []
    },
    "test:integration": {
      "dependsOn": ["build"],
      "outputs": []
    },
    "test:coverage": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    },
    "lint": {
      "outputs": []
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "outputs": []
    }
  }
}

要点：

  • Turbo 2.x 使用 tasks；pipeline 是 1.x 写法，2.x 会直接报错。
  • build.dependsOn: ["^build"] 保证 types → utils → ui → apps 的拓扑顺序。
  • outputs 只声明需要缓存的产物：库包与应用的 dist/**。@tutorial/ui 的 tailwind-preset.cjs 是源码，不属于构建产物，因此不进 outputs。
  • test.dependsOn: ["build"] 指同一包的 build，保证 dist.integration.test.tsx 消费到最新产物；因此 ui 包自身的 test 脚本不再内嵌 pnpm build，避免 Turbo 下双重构建。
  • test:unit 不依赖 build（只测源码）；test:integration 与 test:coverage 声明 dependsOn: ["build"]，因为要读 dist 或渲染整棵跨包组件树。
  • typecheck.dependsOn: ["^build"] 是因为 @tutorial/ui 不再使用源码 paths，类型检查需要先拿到 types / utils 的 dist 声明文件；干净环境直接 tsc --noEmit 会报找不到模块。
  • lint / typecheck 无可缓存产物，outputs: []。

对应的根脚本：

json
{
  "scripts": {
    "build": "TURBO_TELEMETRY_DISABLED=1 turbo run build",
    "build:pnpm": "pnpm build:libs && pnpm -r --filter=./apps/* run build",
    "test": "TURBO_TELEMETRY_DISABLED=1 turbo run test",
    "test:unit": "TURBO_TELEMETRY_DISABLED=1 turbo run test:unit",
    "test:integration": "TURBO_TELEMETRY_DISABLED=1 turbo run test:integration",
    "test:coverage": "TURBO_TELEMETRY_DISABLED=1 turbo run test:coverage",
    "lint": "TURBO_TELEMETRY_DISABLED=1 turbo run lint",
    "typecheck": "TURBO_TELEMETRY_DISABLED=1 turbo run typecheck"
  }
}

build:pnpm 有意保留：只用 pnpm 拓扑构建。缓存行为异常时，可以用它排查“是构建本身的问题，还是 Turbo 的问题”。

缓存命中实测 ​

本地环境：macOS、Node 24、pnpm 9.15.4、Turbo 2.11.10；先删除 dist/ 与 .turbo/，保证冷启动。

命令状态Turbo 计时墙钟耗时
pnpm build:pnpm纯 pnpm 冷构建—8.46s
pnpm build（首次）5 个任务全部 cache miss8.472s9.07s
pnpm build（再次）5 个任务全部命中，FULL TURBO25ms0.58s

解读：

  • 冷构建时 Turbo 与纯 pnpm 基本持平（8~9s）。本项目规模小，并行收益有限，还要额外付出哈希与守护进程开销。
  • 命中缓存后构建从 ~9s 降到 ~0.6s，收益主要来自“整包产物复制”而不是重新编译。
  • 两次构建的 apps/web CSS 完全一致：11,347 bytes，sha256 8d066fa0…，且包含 bg-blue-600。这说明缓存没有改变产物。

远程缓存（本次未启用） ​

Turbo 默认只写本地 .turbo/cache。接入远程缓存的一般步骤：

bash
pnpm dlx turbo login
pnpm dlx turbo link
# CI 中通过环境变量注入
# TURBO_TOKEN=... TURBO_TEAM=... pnpm build

安全边界：

  • 不要把 TURBO_TOKEN 暴露给 pull_request（尤其 fork PR）。缓存是可写共享资源，攻击者可以在 PR 中投毒，让主线命中恶意产物。
  • 只在 push 到可信分支时允许写缓存；fork PR 只读或完全禁用。
  • 远程缓存只存储 outputs 声明的路径，不要把密钥或环境文件放进构建产物目录。
远程缓存签名：TURBO_REMOTE_CACHE_SIGNATURE_KEY ​

远程缓存的信任模型是「命中即复用」——只要产物哈希对得上，Turbo 就会把远端产物解包到工作区，不会重新校验内容。因此只靠 TURBO_TOKEN 只能控制「谁能写」，不能证明「写进去的东西没被篡改」。签名密钥的作用是给缓存条目加一层 HMAC：

bash
# 本地/CI 与缓存服务端都配置同一个密钥
export TURBO_REMOTE_CACHE_SIGNATURE_KEY=...   # 建议 32 字节以上的随机串
export TURBO_TOKEN=...
export TURBO_TEAM=...
pnpm build
  • 必须成对配置：写入方与读取方使用同一个 TURBO_REMOTE_CACHE_SIGNATURE_KEY，否则签名校验失败会退化为缓存未命中（不会报错，只是白跑）。
  • 密钥同样不进仓库：CI 里从 secrets 注入，本地放 shell 环境或用户级配置。
  • 轮换策略：更换密钥等于让远端缓存整体失效，一次构建会回到冷启动，建议在发布低峰期做。

fork PR 的安全边界：

触发方式能否拿到 secrets结论
pull_request（来自 fork）否拿不到 TURBO_TOKEN / 签名密钥，只能退回本地缓存
pull_request（同仓库分支）是可按分支策略决定是否允许写缓存
pull_request_target是禁止在此事件下执行仓库代码并启用远程缓存
push 到 main / tag是允许读写缓存，注入完整凭据

pull_request_target 会把 secrets 暴露给 fork 代码运行的 job；一旦在该事件里 checkout 并执行 PR 代码，外部贡献者就能读到 token、往缓存里写任意产物。所以本仓库的立场是：

  • 默认不启用远程缓存（.github/actions/setup-pnpm 只做 actions/cache 的本地 .turbo 缓存）；
  • 真要启用时，只在可信触发路径（push 到 main、workflow_dispatch、tag）注入 TURBO_TOKEN 与 TURBO_REMOTE_CACHE_SIGNATURE_KEY；
  • fork PR 的作业保持这两个变量为空，缓存写入自然是关闭的。

为什么 docs:build 暂不进 Turbo pipeline ​

pnpm docs:build 约 3~4 秒，输入是 docs/ 与 .vitepress/，与包构建完全独立。放进 pipeline 需要额外声明 .vitepress/dist 作为 outputs、维护失效边界与缓存体积，节省却很有限。因此保持独立 npm script；当文档站构建明显变慢（例如超过 30 秒）或需要在多个作业间复用产物时再评估。

CI 缓存策略（GitHub Actions） ​

yaml
# pnpm store：依赖变更时失效
- uses: actions/cache@v4
  with:
    path: ${{ steps.pnpm-cache.outputs.STORE_PATH }}
    key: ${{ runner.os }}-pnpm-store-${{ hashFiles('pnpm-lock.yaml') }}
    restore-keys: |
      ${{ runner.os }}-pnpm-store-

# Turbo 缓存：key 额外叠加 Turbo 版本，升级时自动失效
- uses: actions/cache@v4
  with:
    path: .turbo
    key: ${{ runner.os }}-turbo-${{ hashFiles('pnpm-lock.yaml') }}-${{ steps.turbo-version.outputs.version }}
    restore-keys: |
      ${{ runner.os }}-turbo-${{ hashFiles('pnpm-lock.yaml') }}-

容器化构建与分层缓存 ​

apps/api 的生产镜像在仓库根目录的 Dockerfile，构建上下文也必须是仓库根目录：

bash
docker build -t pnpm-monorepo-api .

# 无法直连 Docker Hub 时，用 build-arg 把基础镜像指向可达的镜像站
docker build \
  --build-arg NODE_IMAGE=docker.m.daocloud.io/library/node:20-alpine \
  -t pnpm-monorepo-api .

turbo prune 解决什么问题 ​

直接把整个仓库 COPY . . 进镜像，会把 docs/、exercises/、web 应用以及本地 node_modules 一起发送给 daemon。turbo prune 按依赖图裁剪出目标包及其 workspace 依赖：

bash
pnpm dlx turbo@2.11.10 prune @tutorial/api --docker --out-dir out

输出分两部分，正好对应两层缓存：

目录内容用途
out/jsonpnpm-lock.yaml + 各包 package.json先装依赖，源码变化不失效安装层
out/full裁剪后的源码、tsconfig、turbo.json 等构建阶段使用

实测 Turbo 2.11.10 的 prune 能正确处理 catalog: 与 workspace:*，输出只保留 @tutorial/api、@tutorial/types、@tutorial/utils。注意它不会带上根目录的共享构建脚本与 TS 基础配置，Dockerfile 需要显式补：

dockerfile
COPY --from=pruner /app/tsconfig.json /app/tsconfig.base.json ./
COPY --from=pruner /app/scripts ./scripts

pnpm deploy 解决什么问题 ​

构建阶段结束后，直接把整个 workspace 的 node_modules 复制进运行镜像会带上 devDependencies，还会保留指向 .pnpm 的 symlink 结构。pnpm deploy 会：

  1. 按目标包的 files 字段复制运行所需文件（apps/api 声明了 "files": ["dist"]，因此不含 src/、tsconfig.json、.turbo/）；
  2. 把 workspace:* 解析成真实包目录（node_modules/@tutorial/types 指向 .pnpm/@tutorial+types@file+packages+types，内含构建好的 dist）；
  3. 只安装生产依赖。

实测部署目录：

text
/prod/api
├── dist/            # 8 KB
├── node_modules/    # ~4.1 MB，顶层只有 @tutorial、cors、express、mime-types
└── package.json

typescript、vitest、tsx、eslint 均不在运行镜像中。package.json 里仍然保留 devDependencies 字段，但依赖并未安装。

BuildKit cache mount ​

dockerfile
RUN --mount=type=cache,id=pnpm-store,target=/pnpm/store \
    pnpm install --frozen-lockfile
  • pnpm store 是内容寻址的，mount 后下载过的 tarball 不会写进镜像层，也不会因为删除而重复下载；
  • 与 turbo prune 的 out/json 配合：lockfile 不变时安装层直接命中缓存，源码改动只会让构建层失效；
  • 需要 BuildKit（Docker Desktop 默认开启，CI 中用 docker/setup-buildx-action）。

完整 Dockerfile（与仓库实际文件一致） ​

dockerfile
ARG NODE_IMAGE=node:20-alpine

FROM --platform=$BUILDPLATFORM ${NODE_IMAGE} AS builder

ENV PNPM_HOME=/pnpm \
    PATH=/pnpm:$PATH \
    npm_config_store_dir=/pnpm/store \
    TURBO_TELEMETRY_DISABLED=1

RUN corepack enable && corepack prepare pnpm@9.15.4 --activate

WORKDIR /app

FROM builder AS pruner
COPY . .
RUN --mount=type=cache,id=pnpm-store,target=/pnpm/store \
    pnpm dlx turbo@2.11.10 prune @tutorial/api --docker --out-dir out

FROM builder AS installer
COPY --from=pruner /app/out/json/ ./
RUN --mount=type=cache,id=pnpm-store,target=/pnpm/store \
    pnpm install --frozen-lockfile

COPY --from=pruner /app/out/full/ ./
COPY --from=pruner /app/tsconfig.json /app/tsconfig.base.json ./
COPY --from=pruner /app/scripts ./scripts
RUN pnpm exec turbo run build --filter=@tutorial/api

FROM installer AS deployer
RUN --mount=type=cache,id=pnpm-store,target=/pnpm/store \
    pnpm --filter @tutorial/api deploy --prod --frozen-lockfile /prod/api

FROM ${NODE_IMAGE} AS runner
ENV NODE_ENV=production PORT=3000
WORKDIR /app

RUN addgroup -S app && adduser -S -G app app

COPY --from=deployer --chown=app:app /prod/api/ ./
USER app

EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD wget -q -O /dev/null "http://127.0.0.1:${PORT}/healthz" || exit 1

CMD ["node", "dist/index.js"]

多架构构建时，构建阶段固定在 $BUILDPLATFORM 上执行（避免在 QEMU 里跑 tsc/pnpm），只有运行阶段按目标架构展开：

bash
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --build-arg NODE_IMAGE=docker.m.daocloud.io/library/node:20-alpine \
  -t pnpm-monorepo-api .

多架构导出到本地镜像仓库需要 --push 或 containerd image store；只做构建验证时可以加 --output type=oci,dest=api.tar。

多包并行构建策略 ​

pnpm 原生并行 ​

bash
# 并行构建所有包（默认按拓扑顺序）
pnpm -r --parallel run build

# 限制并发数（默认 4）
pnpm -r --parallel --workspace-concurrency=4 run build

# 仅构建有变更的包（基于依赖图）
pnpm -r --filter ...[origin/main] run build

拓扑排序构建 ​

bash
# 按依赖拓扑顺序构建（串行但保证依赖先构建）
pnpm -r run build

# 并行构建（忽略拓扑，需确保依赖已构建）
pnpm -r --parallel run build

条件构建 ​

bash
# 仅构建有 build 脚本的包
pnpm -r --if-present run build

# 仅构建特定目录
pnpm -r --filter ./packages/* run build

# 构建依赖 @tutorial/ui 的所有包
pnpm -r --filter ...@tutorial/ui run build

构建性能优化 ​

1. 排除测试文件 ​

json
// tsconfig.build.json
{
  "exclude": ["**/*.test.ts", "**/*.spec.ts", "**/__tests__/**"]
}

2. 减少声明文件生成 ​

json
// 开发环境跳过类型检查
{
  "compilerOptions": {
    "skipLibCheck": true,
    "declaration": false // 仅生产构建生成 .d.ts
  }
}

3. 使用 esbuild/swc 替代 tsc ​

bash
# 安装 esbuild
pnpm add -D esbuild

# 构建脚本
esbuild src/index.ts --bundle --outfile=dist/index.js --format=esm

4. 并行类型检查 ​

json
// package.json
{
  "scripts": {
    "build": "vite build",
    "typecheck": "tsc --noEmit" // 与构建并行执行
  }
}
