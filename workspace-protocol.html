06 · workspace:* 协议与依赖解析 ​

阅读时长：20 分钟　|　前置要求：读完 04 包创建与依赖声明、05 依赖共享与 Hoisting　|　配套练习：E2

第 04 章讲了「怎么声明依赖」，这一章要把它彻底讲穿：workspace:* 到底是什么意思、和 workspace:^ 有什么区别、发布时它们如何被改写、pnpm 又凭什么在「本地包」和「registry 版本」之间做选择。这是 Monorepo 里最容易踩坑、也最值得一次搞懂的一节。

你将学到 ​

  • workspace:* / workspace:^ / workspace:~ 三种协议的语义差异
  • link-workspace-packages 与 prefer-workspace-packages 如何决定「本地还是远程」
  • save-workspace-protocol=rolling 让 pnpm add 自动写入哪种协议
  • 发布时协议如何被替换成真实版本号
  • --filter 选择器速查（... 前缀/后缀的语义）

一、三种 workspace 协议 ​

workspace: 协议是 pnpm 的私有协议，只在本仓库内有效，它告诉 pnpm：「这个依赖指向工作区的某个包，不要去 registry 找」。

写法本地开发时发布（pnpm publish / pnpm pack）后改写为
workspace:*链接本地包精确版本，如 "1.2.3"
workspace:^链接本地包^ 范围，如 "^1.2.3"
workspace:~链接本地包~ 范围，如 "~1.2.3"
workspace:1.2.3链接本地包"1.2.3"（显式指定，语义等价于 workspace:*）

💡 关键点：在仓库内，三者行为完全一致（都链本地）；差别只在发布后外部用户拿到的是精确版本还是范围。所以这个选择只对「会被发布出去的包」有意义。

该选哪一个 ​

你的包会被发布吗推荐写法理由
否（纯私有应用）workspace:*语义最直白，省心
是（会发到 registry）workspace:^发布后留出范围，使用者升级依赖更灵活
是，且需要严格锁版本workspace:~ 或 workspace:*避免使用者自动跳到下一个 minor

本教程的 apps/* 都是私有应用，因此统一使用 workspace:*；packages/ui 这种可发布库则更适合 workspace:^。

二、解析优先级：本地还是 registry？ ​

即使你不写 workspace: 协议、只写普通版本号，pnpm 也可能把依赖链到本地包。这由两个开关决定：

配置项作用本仓库取值
link-workspace-packages版本范围能匹配本地包时，是否自动链本地（而非下载 registry 版本）true
prefer-workspace-packages即便 registry 上有满足范围的版本，是否仍优先选本地包true

粗略的判定顺序可以记成：

text
写了 workspace: 协议        → 一定链本地（协议强制）
未写协议 + link-workspace-packages=true
       → 本地版本满足范围？ → 视 prefer-workspace-packages 决定
       → 本地版本不满足范围 → 下载 registry 版本（此时两边会出现同名不同源，危险！）

⚠️ 踩坑高发区：apps/web 写 "@tutorial/ui": "^1.0.0"，但 packages/ui 本地版本是 2.0.0（不满足 ^1.0.0），pnpm 会从 registry 拉一个 1.x 的 @tutorial/ui——如果 registry 上真存在同名包，你本地改的代码就完全不生效。

最佳实践：内部依赖一律显式写 workspace: 协议，不要依赖自动链接。

⚠️ 各 pnpm 大版本对这两个配置的默认值曾有调整，别背「默认值」，用命令确认当前生效值：

bash
pnpm config get link-workspace-packages
pnpm config get prefer-workspace-packages

三、save-workspace-protocol：pnpm add 写入什么协议 ​

当你用 pnpm add 添加一个「恰好是本地包」的依赖时，pnpm 写进 package.json 的协议由 save-workspace-protocol 决定：

取值pnpm add @tutorial/utils 写入
rolling（默认）"@tutorial/utils": "workspace:^"
true"@tutorial/utils": "workspace:*"
false普通 semver 范围，如 "^1.0.0"

本仓库 .npmrc 设置了 save-workspace-protocol=rolling，所以 pnpm add @tutorial/xxx 会自动带上 workspace:^。若你更希望锁死精确本地版本，把它改成 true。

bash
# 实操：观察协议是如何被写入的
pnpm --filter @tutorial/web add @tutorial/utils
# 打开 apps/web/package.json，会看到 "@tutorial/utils": "workspace:^"

四、发布时的版本改写 ​

这是 workspace: 协议设计得最巧妙的地方：仓库内用链接，发布时替换成真实版本号，外部使用者完全感知不到协议的存在。

jsonc
// 发布前（packages/ui/package.json）
{
  "name": "@tutorial/ui",
  "version": "1.2.3",
  "dependencies": {
    "@tutorial/utils": "workspace:^",
  },
}
jsonc
// 执行 pnpm publish 后，registry 上真正生效的元数据
{
  "name": "@tutorial/ui",
  "version": "1.2.3",
  "dependencies": {
    "@tutorial/utils": "^1.2.3", // workspace:^ → ^<当前本地版本>
  },
}

改写发生在 pnpm publish / pnpm pack 打包阶段，源文件不会被修改。版本号从哪里来？就是被引用包当前在 package.json 里的 version。

⚠️ 因此：发布前必须先让被依赖的包完成版本递增（第 08 章的 Changesets 就是干这个），否则改写出的范围会指向一个并未发布的新版本。

五、--filter 选择器速查 ​

Monorepo 里「只操作某几个包」全靠 --filter。它与 workspace: 协议配合，是日常最高频的操作：

写法含义
--filter @tutorial/web精确匹配包名
--filter ./apps/*按目录路径匹配（也支持 --filter {./apps}）
--filter @tutorial/utils...utils 及其依赖（后缀 ...）
--filter ...@tutorial/utilsutils 及其依赖者（前缀 ...）
--filter @tutorial/utils^...仅 utils 的依赖，不含自身
--filter ...^@tutorial/utils仅 utils 的依赖者，不含自身
--filter ...[origin/main]自某次提交以来发生变更的包
--filter "!@tutorial/api"排除某个包
bash
# 常见用法
pnpm --filter @tutorial/web test            # 只测 web
pnpm --filter ./packages/* build            # 只构建 packages 层
pnpm -r --filter ...@tutorial/types build   # 构建所有依赖 types 的包（含传递依赖者）
pnpm -r --filter ...[origin/main] typecheck # 只检查改动过的包（CI 提速利器）

-r 与 --filter 的关系：-r（recursive）表示「遍历工作区所有包」；--filter 在其上做筛选。pnpm -r run build 会按依赖拓扑顺序执行（被依赖者先跑），这背后的调度原理见原理篇 P4。

常见陷阱 ​

  • 协议写错方向：workspace:* 用来锁本地最新代码，别指望它「发布后还保持 *」——它会被改写成精确版本。
  • 混用两种来源：内部依赖既写 workspace: 又写普通版本号，前者覆盖后者，容易造成困惑；统一用一种。
  • 忘记 -w：在仓库根安装「根级别」工具（如 vitepress、eslint）必须加 -w（pnpm add -w -D xxx），否则 pnpm 会报错或装错位置。
  • workspace:* 在非 workspace 上下文：把带 workspace:* 的 package.json 单独复制到别处执行 npm install 会直接失败——它是 pnpm 专属协议。
