私有包创建流程 ​

步骤 1：创建目录与 package.json ​

bash
mkdir -p packages/my-new-package/src
cd packages/my-new-package
json
{
  "name": "@tutorial/my-new-package",
  "version": "1.0.0",
  "private": true,
  "description": "新创建的共享包",
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "exports": {
    ".": "./src/index.ts"
  },
  "scripts": {
    "build": "tsc",
    "test": "vitest run",
    "lint": "eslint src --ext .ts"
  },
  "dependencies": {},
  "devDependencies": {
    "typescript": "catalog:"
  }
}

上例是“尚未决定发布方式”的初始状态。需要发布的包应移除 private，并按步骤 3 的“产物消费”配置；本仓库的 types / utils / ui 已完成切换，apps/* 继续保持 private: true。

步骤 2：设置命名空间（scope） ​

json
{
  "name": "@org-name/package-name"
}
命名方式示例适用场景
无 scopemy-utils小型项目，简单包名
有 scope@myorg/utils企业级项目，避免包名冲突
@types@types/reactTypeScript 类型定义（社区约定）

步骤 3：定义入口点 ​

共享包有两种消费方式，区别在于 exports 指向源码还是构建产物：

模式入口指向适用阶段本仓库现状
源码消费src/*.ts应用与共享包在同一 workspace，改完即生效应用侧可用别名临时指向源码，但包本身不应发布该形态
产物消费dist/...需要 pnpm pack / 发布，消费方拿不到源码@tutorial/types、@tutorial/utils、@tutorial/ui

产物消费的 package.json 示例（ESM + CJS 双格式）：

json
{
  "main": "./dist/cjs/index.js",
  "module": "./dist/esm/index.js",
  "types": "./dist/cjs/index.d.ts",
  "exports": {
    ".": {
      "import": {
        "types": "./dist/esm/index.d.ts",
        "default": "./dist/esm/index.js"
      },
      "require": {
        "types": "./dist/cjs/index.d.ts",
        "default": "./dist/cjs/index.js"
      }
    }
  },
  "files": ["dist"]
}

几个关键点：

  • dist/esm 与 dist/cjs 各放一个 package.json（分别为 {"type":"module"} 与 {"type":"commonjs"}），Node 才会按正确格式加载产物。
  • files 是白名单，只有 dist 会进入 tarball；源码与测试不会被打包。
  • 切换方式：先执行 pnpm build:libs 生成产物，再把 exports 从 src 改为 dist。根 test / dev / build 已配置为自动先构建共享包，避免消费到过期产物。
  • @tutorial/ui 额外导出了 ./tailwind-preset 子路径，样式契约见下文。

@tutorial/ui 的样式契约：Tailwind preset ​

组件库不产出 CSS，而是把“需要扫描哪些文件”固化成 preset。packages/ui/tailwind-preset.cjs 用 __dirname 判断当前形态：

  • 本地 workspace：存在 src/，扫描 packages/ui/src/**/*.{ts,tsx}；
  • 安装后的发布包：只有 dist/，扫描 node_modules/@tutorial/ui/dist/**/*.{js,cjs,mjs}。
js
// packages/ui/tailwind-preset.cjs（核心逻辑）
const fs = require("node:fs");
const path = require("node:path");

const content = [];
if (fs.existsSync(path.join(__dirname, "src"))) {
  content.push(`${__dirname}/src/**/*.{ts,tsx}`);
}
if (fs.existsSync(path.join(__dirname, "dist"))) {
  content.push(`${__dirname}/dist/**/*.{js,cjs,mjs}`);
}

module.exports = { content, theme: { extend: {} }, plugins: [] };

通过 exports 暴露给消费方：

json
{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/esm/index.d.ts",
        "default": "./dist/esm/index.js"
      },
      "require": {
        "types": "./dist/cjs/index.d.ts",
        "default": "./dist/cjs/index.js"
      }
    },
    "./tailwind-preset": {
      "types": "./tailwind-preset.d.ts",
      "default": "./tailwind-preset.cjs"
    }
  },
  "files": ["dist", "tailwind-preset.cjs", "tailwind-preset.d.ts"]
}

应用侧只需要引入 preset，不再硬编码组件库目录：

js
// apps/web/tailwind.config.js
import uiPreset from "@tutorial/ui/tailwind-preset";

export default {
  presets: [uiPreset],
  // Tailwind v3 对 preset.content 的合并行为不稳定，显式展开更可靠
  content: [...uiPreset.content, "./index.html", "./src/**/*.{ts,tsx}"],
};

为什么这么做：

  • 同一份 preset 同时服务 workspace 开发与 pnpm pack 后的发布包，消费方不需要知道仓库目录结构；
  • 不再需要 styles.css 导出，避免 CSS 路径在 ESM/CJS 与不同打包器之间产生歧义；
  • 样式仍由应用侧 Tailwind 生成，组件库只声明扫描范围，主题扩展也可在 preset 的 theme.extend 中集中维护。

注意：实测 Tailwind v3 不会可靠合并 preset 里的 content，所以要写 content: [...uiPreset.content, ...]，而不是只写 presets: [uiPreset]。

bash

跨包依赖声明 ​

依赖类型对比 ​

依赖类型安装位置用途示例
dependencies生产依赖运行时必需react、lodash
devDependencies开发依赖构建/测试工具typescript、vitest
peerDependencies宿主提供需宿主环境提供react、react-dom
optionalDependencies可选依赖失败不影响安装fsevents
bundledDependencies打包依赖随包一起发布较少使用

workspace: 协议使用场景 ​

json
// package.json
{
  "dependencies": {
    // 始终链接到本地最新版本（开发推荐）
    "@tutorial/types": "workspace:*",

    // 链接到本地版本，遵循语义化版本
    "@tutorial/utils": "workspace:^1.0.0",

    // 第三方依赖使用正常版本号
    "lodash": "^4.17.21"
  }
}

命令行安装 vs 手动编辑 ​

bash
# 安装第三方依赖到某个包
pnpm add lodash --filter @tutorial/web

# 安装 workspace 包（自动添加 workspace:*）
pnpm add @tutorial/types --filter @tutorial/web --workspace

# 安装 devDependency
pnpm add -D typescript --filter @tutorial/web

# 安装到根 package.json（共享工具）
pnpm add -Dw @changesets/cli

peerDependencies 显式声明 ​

为什么需要 peerDependencies？ ​

场景：UI 组件库 @tutorial/ui 依赖 React，但不应将 React 打包到组件库中（否则应用会有多个 React 实例）。

json
// packages/ui/package.json
{
  "peerDependencies": {
    "react": ">=18.0.0",
    "react-dom": ">=18.0.0"
  },
  "peerDependenciesMeta": {
    "react-dom": {
      "optional": true // react-dom 是可选的 peer 依赖
    }
  }
}

.npmrc 配置控制 ​

ini
# .npmrc

# strict-peer-dependencies: 严格检查 peer 版本
# true: 版本不匹配直接报错（推荐开发期开启）
# false: 仅警告，不阻止安装（默认）
strict-peer-dependencies=true

# auto-install-peers: 自动安装缺失的 peer 依赖
# true: 自动安装（默认，解决 React 库常见警告）
# false: 不自动安装，需手动添加
auto-install-peers=true

peer 依赖冲突解决 ​

错误示例：
├─ @tutorial/ui
│   └─ peer react@>=18.0.0
└─ @tutorial/legacy-ui
    └─ peer react@^17.0.0

冲突：应用需要同时安装 react@17 和 react@18（不可能）

解决方案：

json
// 根 package.json 统一声明
{
  "dependencies": {
    "react": "^18.2.0",
    "react-dom": "^18.2.0"
  }
}
ini
# .npmrc 降级冲突为警告
strict-peer-dependencies=false

依赖版本冲突解决 ​

场景分析 ​

packages/web/package.json:
  "lodash": "^4.17.21"

packages/api/package.json:
  "lodash": "^4.17.15"

pnpm 的处理方式：

  • 解析满足两个约束的最高版本：4.17.21
  • 两个包共享同一个 lodash@4.17.21 实例（硬链接）

冲突类型与解决方案 ​

冲突类型表现解决方案
兼容版本冲突^4.17.15 vs ^4.17.21pnpm 自动解析到兼容的最高版本
主版本冲突^3.0.0 vs ^4.0.0使用 pnpm.overrides 统一版本
传递依赖冲突A -> lodash@3, B -> lodash@4显式声明 overrides
幽灵依赖隐式依赖未声明开启 strict-peer-dependencies

使用 pnpm.overrides 强制统一版本 ​

json
// package.json
{
  "pnpm": {
    "overrides": {
      // 强制所有 lodash 依赖使用 4.17.21
      "lodash": "4.17.21",

      // 仅覆盖特定包的传递依赖
      "@some/package>lodash": "4.17.21",

      // 使用本地 workspace 包覆盖 registry 版本
      "@tutorial/types": "workspace:*"
    }
  }
}

使用 catalog 统一管理版本（pnpm 9.x+） ​

yaml
# pnpm-workspace.yaml
catalog:
  "typescript": "^5.3.3"
  "react": "^18.2.0"
  "react-dom": "^18.2.0"
json
// packages/ui/package.json
{
  "dependencies": {
    "react": "catalog:" // 自动使用 workspace catalog 中的版本
  }
}

私有源与作用域 registry ​

本仓库的 .npmrc 只配置公开源（registry.npmmirror.com），不包含任何私有源与凭据。需要接私有 registry 时，用仓库根目录的 .npmrc.example 作为模板，不要直接改仓库 .npmrc 的默认源。

为什么只改 scope，不改默认 registry ​

ini
# 只把 @acme 这个 scope 指到私有源
@acme:registry=https://npm.example.com/artifactory/api/npm/npm-private/
  • 只影响 @acme/* 包，公共依赖仍走默认源；私有源故障不会拖垮整次安装。
  • 如果把 registry= 全局改成私有源，所有公共依赖都要经过私有源代理，镜像缺包时会出现大面积 404。
  • 作用域 name 必须与 package.json 里的包名一致（@acme/utils 对应 @acme）。

凭据用环境变量占位 ​

ini
//npm.example.com/artifactory/api/npm/npm-private/:_authToken=${NPM_TOKEN}
  • pnpm / npm 会展开 .npmrc 里的 ${VAR}，文件本身不含真实 token，可安全地进版本库或配置模板。
  • _authToken 前面的路径必须与 registry 的「主机 + 路径前缀」一致；只写 //npm.example.com/:_authToken= 表示该主机下所有源共用。
  • token 通过 shell 环境变量注入：
bash
export NPM_TOKEN=xxxxx          # 本地，仅当前 shell 有效
pnpm install                    # pnpm 安装时会读取 NPM_TOKEN

CI 里用 secrets 注入，而不是写进文件：

yaml
- name: Configure private registry
  env:
    NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
  run: |
    printf '@acme:registry=https://npm.example.com/artifactory/api/npm/npm-private/\n' >> ~/.npmrc
    printf '//npm.example.com/artifactory/api/npm/npm-private/:_authToken=${NPM_TOKEN}\n' >> ~/.npmrc

与发布流程的两套变量 ​

场景变量说明
安装私有依赖NPM_TOKEN（.npmrc 内 ${}）供 pnpm 读取 registry 凭据
发布到公共 npmNODE_AUTH_TOKENnpm CLI 约定，release.yml 已按此实现
发布时指定目标 registryNPM_CONFIG_REGISTRY与安装阶段的作用域源互不影响

注意：仓库 .npmrc 的 registry=https://registry.npmmirror.com 保持不变；私有源只通过 scope 声明叠加，避免把教程仓库变成某家私有源的绑定配置。真实的 NPM_TOKEN 永远不进仓库，release.yml 在没有 token 时自动走 dry-run。

依赖图治理与循环依赖 ​

当前基线是 5 个 workspace 包、8 条 workspace 边、0 个环：apps 位于上层，packages 之间按 types → utils → ui 单向展开。完整图见本章开头的 SVG。

治理规则 ​

规则说明
apps/* 只能依赖 packages/*禁止 app 之间互相依赖，避免部署边界混乱
packages/* 不得反向依赖 apps/*库包不能知道任何应用的存在
@tutorial/api 不得依赖 @tutorial/ui服务端不引入浏览器组件库
workspace 包之间禁止循环循环会破坏拓扑构建与增量缓存
workspace 依赖必须写 workspace:*避免本地误用 registry 上的旧版本
源码 import 必须已声明防止 phantom dependency 借上层依赖“搭便车”

exercises/* 默认不参与治理：它们是独立练习，不应被主仓库的依赖方向约束。

实现方式：scripts/check-deps.mjs ​

没有引入 dependency-cruiser。原因是当前需要的规则都是包级结构检查：

  • 直接读取 apps/*、packages/* 的 package.json，构造 workspace 依赖图；
  • 循环依赖用 DFS 找回边；
  • phantom dependency 用正则扫描源码里的 from / import() / require()，去注释后与声明字段比对。

脚本约 250 行（含注释）、零新增依赖，足够覆盖上述规则。dependency-cruiser 的优势是能解析路径别名、动态 import 和更细的文件级依赖，但需要额外依赖与配置；等仓库出现 tsconfig 路径别名或复杂动态加载时再评估引入。

bash
pnpm deps:check

循环依赖的解决方案 ​

  1. 提取公共依赖：将循环依赖提取为新的独立包
  2. 重构代码：通过依赖注入或事件机制解耦
  3. 合并包：如果循环依赖说明包拆分过细，考虑合并

最佳实践 ​

1. 最小化依赖原则 ​

json
// 反例：引入不必要的重型库

    "typescript": "^5.3.3" // 构建时才需要
