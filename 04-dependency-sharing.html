pnpm 存储机制 ​

内容寻址存储（Content-Addressable Store） ​

~/.pnpm-store/
├── v3/
│   ├── files/          # 实际文件内容（按内容哈希存储）
│   │   ├── 00/xxxxx    # 文件哈希前两位作为目录名
│   │   └── ...
│   └── packages/       # 包元数据
│       └── lodash@4.17.21/
│           └── index.json

核心优势：

  • 同一台机器上的所有项目共享存储
  • 安装新包时，若内容已存在，仅需创建硬链接（0 拷贝）
  • 节省 80%+ 磁盘空间

硬链接 vs 软链接 ​

特性硬链接软链接（符号链接）
指向文件 inode文件路径
源文件删除仍可访问失效（ dangling ）
跨文件系统不支持支持
pnpm 用途store -> node_modules/.pnpm.pnpm -> 项目 node_modules

安装过程图解 ​

安装 lodash@4.17.21：

1. 下载 tarball 到缓存
   npm registry → ~/.pnpm-cache/lodash-4.17.21.tgz

2. 解压到 store
   ~/.pnpm-cache/... → ~/.pnpm-store/v3/files/...

3. 创建硬链接到项目
   ~/.pnpm-store/v3/files/... → node_modules/.pnpm/lodash@4.17.21/node_modules/lodash/...

4. 创建软链接到依赖树
   node_modules/.pnpm/lodash@4.17.21/node_modules/lodash
     → node_modules/lodash（如果 hoist）

node_modules 结构可视化 ​

pnpm 的严格结构 ​

project/
├── node_modules/
│   ├── .pnpm/                    # 所有依赖的实际存储位置
│   │   ├── lodash@4.17.21/
│   │   │   └── node_modules/
│   │   │       └── lodash/       # 实际文件（硬链接自 store）
│   │   │
│   │   ├── react@18.2.0/
│   │   │   └── node_modules/
│   │   │       └── react/
│   │   │
│   │   └── .modules.yaml         # 模块依赖关系元数据
│   │
│   ├── lodash -> .pnpm/lodash@4.17.21/node_modules/lodash  # 软链接（如果 hoist）
│   ├── react -> .pnpm/react@18.2.0/node_modules/react
│   │
│   └── .bin/                     # CLI 命令入口
│
└── package.json

与 npm 的结构对比 ​

npm（扁平结构）：

node_modules/
├── lodash/           # 被提升到根
├── react/            # 被提升到根
├── some-lib/         # 依赖 lodash
└── other-lib/        # 也依赖 lodash（共享同一实例）
    └── node_modules/
        └── lodash/   # 如果版本冲突，嵌套安装

pnpm（严格嵌套 + 软链接）：

node_modules/
├── .pnpm/
│   ├── lodash@4.17.21/
│   ├── lodash@3.10.1/   # 版本冲突时两个版本共存
│   └── some-lib/
│       └── node_modules/
│           └── lodash -> ../../lodash@4.17.21/node_modules/lodash
└── lodash -> .pnpm/lodash@4.17.21/node_modules/lodash  # 仅 hoist 时存在

Hoisting 行为控制 ​

什么是 Hoisting？ ​

Hoisting（提升）是指将依赖从 .pnpm 目录软链接到项目根 node_modules，使其可被全局访问。

配置项详解 ​

ini
# .npmrc

# hoist: 是否启用 hoisting（默认 true）
# true:  部分依赖被提升到根 node_modules
# false: 无提升，所有依赖仅在 .pnpm 中可见
hoist=true

# hoist-pattern: 哪些包被提升（默认 ['*']）
# 可精确控制提升范围，避免污染全局空间
hoist-pattern[]=*
# hoist-pattern[]=*eslint*      # 仅提升 eslint 相关
# hoist-pattern[]=*prettier*    # 仅提升 prettier 相关

# public-hoist-pattern: 提升到项目根（对所有包可见）
# 场景：类型定义、构建工具需要全局可见
public-hoist-pattern[]=*types*
public-hoist-pattern[]=*eslint*
public-hoist-pattern[]=*prettier*

# shamefully-hoist: 兼容 npm 的完全扁平结构（默认 false）
# true:  模拟 npm 的扁平 node_modules
# false: 保持 pnpm 的严格隔离（推荐）
shamefully-hoist=false

配置对比表 ​

配置组合node_modules 结构适用场景
hoist=true + shamefully-hoist=false部分提升，严格隔离默认推荐，大多数项目
hoist=false无提升，完全隔离追求极致安全，避免任何幻影依赖
shamefully-hoist=true完全扁平迁移旧项目（临时方案）

hoist-pattern 实战示例 ​

ini
# .npmrc

# 仅提升类型定义（TypeScript 需要全局可见）
hoist-pattern[]=!*                # 先禁用所有
hoist-pattern[]=*@types*          # 再仅启用 @types

# 或者更精细控制
public-hoist-pattern[]=*@types/node
public-hoist-pattern[]=*@types/react

依赖版本统一管理 ​

根 package.json 集中管理 ​

json
// package.json
{
  "devDependencies": {
    "typescript": "^5.3.3",
    "vitest": "^1.2.0",
    "eslint": "^8.56.0"
  }
}

子包通过 workspace:* 引用根配置：

json
// packages/ui/package.json
{
  "devDependencies": {
    "typescript": "workspace:*"
  }
}

使用 pnpm.overrides 强制统一 ​

json
{
  "pnpm": {
    "overrides": {
      "typescript": "5.3.3",
      "react": "^18.2.0"
    }
  }
}

Catalog 功能（pnpm 9.x+） ​

yaml
# pnpm-workspace.yaml
catalog:
  "typescript": "^5.3.3"
  "react": "^18.2.0"
  "vitest": "^1.2.0"

  "catalog:default":

json
// package.json
{
  "devDependencies": {
    "typescript": "catalog:default",
    "react": "catalog:"
  }
}

Phantom Dependency 防护 ​

什么是幻影依赖？ ​

js
// 代码中直接使用了 lodash
import _ from "lodash";

// 但 package.json 中并未声明 lodash！
// 之所以能运行，是因为某个依赖（如 some-lib）依赖了 lodash，
// npm 将其扁平化后，lodash 出现在根 node_modules

风险：一旦 some-lib 移除 lodash 依赖，代码立即崩溃。

pnpm 的天然防护 ​

pnpm 的严格隔离结构天然防止幻影依赖：

# pnpm 结构下，lodash 仅在 .pnpm/lodash@x.x.x 中可见
# 如果 package.json 未声明 lodash，import 'lodash' 会直接报错

显式声明所有依赖 ​

json
// package.json（最佳实践）
{
  "dependencies": {
    "lodash": "^4.17.21" // 即使某个依赖也依赖 lodash，仍需显式声明
  }
}

使用 ESLint 检测幻影依赖 ​

json
// .eslintrc.js
module.exports = {
  plugins: ['import'],
  rules: {
    'import/no-extraneous-dependencies': ['error', {
      devDependencies: ['**/*.test.ts', '**/*.config.ts']
    }]
  }
};

最佳实践 ​

1. 保持 hoist=false 以追求极致安全 ​

ini
# .npmrc
hoist=false

代价：某些旧包可能因找不到隐式依赖而报错，需逐一修复。

2. 使用 public-hoist-pattern 精确控制 ​

ini
# .npmrc
# 仅提升类型定义和 lint 工具
public-hoist-pattern[]=*@types*
public-hoist-pattern[]=*eslint*

3. 定期清理 store ​

bash
# 移除未引用的包（节省磁盘）
pnpm store prune

# 查看 store 大小
pnpm store status
